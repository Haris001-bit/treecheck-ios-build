# Production engine rules

- Employee production estimates come only from src/lib/production/engine.ts (pure, versioned) and never use climber-entered crew/hours, because every screen must produce the same estimate and predictions must be measurable against sub input.
- Company operating_model defaults to subcontractors; the Production Plan appears only for employees/hybrid, because the Timber sub workflow must stay untouched.
- Calibration keeps AI-inferred and owner-confirmed characteristics separately and locks the prediction once saved, because photo-reading errors must be distinguishable from Production Engine errors.
- Calibration photos go only through calibration-analyze, never scout-submit. Every calibration detail comes from the live Scout n8n webhook, sent the same fields as a Scout photo (photos, address, service, tape size, cleaned notes, company guidance), and parsed from its notes by _shared/calibrationWebhook.ts; calibration-estimate-callback only saves that reading (no texts, jobs, learning rows or price). Because Mark wants calibration read by exactly the AI that prices live Scout, and scout-submit dispatches real alerts.
- Owners never enter an address for calibration: calibration-analyze fills the webhook's address field with a fixed hidden stand-in (CALIBRATION_STAND_IN_ADDRESS) that is never shown or saved, because the webhook requires one but the job's location doesn't matter for reading the tree.
- Calibration dropdowns offer only Scout's own answer names from supabase/functions/_shared/scoutChoices.ts (no prices or percentages), mapped there to engine values, and the confirmed details keep the chosen name as scoutLabel, because owners must confirm in Scout's wording and Scout's prompt is proprietary.
- Selling price lives in production_pricing_history, never in production calibration, because price must not drive crew/hour predictions.
- Large-company prices come only from the pure, versioned modules beside engine.ts (rules.ts for the rate card schema and PRICING_ENGINE_VERSION, pricing.ts for the price math), and the server recomputes every price from the published rate card on save, because the screen, the stored estimate and the Jobber quote must match.
- A published production rate card never changes (a trigger refuses it): edit a draft and publish a new version, because every estimate stays tied to the card version it was quoted from.
- The AI only fills answers through aiFacts.ts; it never sets a price or edits a rate card, and contradictions in a price sheet go to an admin (contradictions.ts) instead of being guessed, because prices must come from the company's own published rules.
- supabase/functions/_shared/production is generated by scripts/sync-production-engine.mjs; edit the source here and re-run it, never the copy, because sharedCopy.test.ts fails and the server would price differently from the screens.
- docs/demo/demo_production_setup.sql (the expo demo's crew company, Big Oak Tree Co.) is generated from src/lib/production/demo by its test; change bigOak.ts and regenerate (UPDATE_DEMO_SQL=1), never edit the SQL by hand, because the test fails and the demo would stop matching what the engine prices.
- The Jobber approval extras (jobberExtras.ts here, productionJobberExtras.ts on the server) stay switched off until production_rollout.jobber_extras is set after Jobber approves the app's extra permissions; a send never fails on them (a definite refusal resends the quote once without them), because the plain quote must keep working for every company. Hours from Jobber's time sheets go into production_packets.actuals.fromJobber only, never over hours someone saved, and reports count only saved hours (actuals.manHours), because a forgotten timer must not reach the reports unchecked.
